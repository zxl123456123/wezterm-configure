# 文档维护与归档规范

本文档用于说明终端工作台项目中 `docs/` 相关文档的组织方式、维护流程和归档约定，供 AI 代理与维护者参考。

以下通用示例用于说明文档维护方法，不是本项目的功能或性能测量结果。

## 文档内容原则

### 核心原则：记录"代码里看不到"的信息

文档的价值不是重复代码，而是提供上下文、意图、权衡。

### 必须记录的内容

#### 1. 设计意图（Why）

❌ 错误：使用文件系统存储规划文档
✅ 正确：使用文件系统存储规划文档（原因：便于版本控制、跨平台共享、人类可读）

#### 2. 权衡决策（Trade-offs）

记录"为什么选A不选B"：

| 方案 | 优势 | 劣势 | 是否采纳 |
|------|------|------|---------|
| 文件系统 | 版本控制、跨平台、可读 | 需要手动管理 | ✅ 采纳 |
| 数据库 | 查询方便 | 复杂度高、不便版本控制 | ❌ 过度工程 |
| 纯内存 | 最快 | 无持久化 | ❌ 不满足需求 |

#### 3. 系统边界与约束（Constraints）

记录影响设计的关键约束：

**示例**：
- **平台支持**：VSCode 和 Claude Code，未来扩展到 Cursor、Warp
- **文档存储**：docs/current/ 用于活跃规划，docs/archive/ 用于归档
- **跨平台兼容**：工作流数据（docs/）平台无关，配置文件平台隔离

#### 4. 量化数据（Metrics）

代码里看不到的性能数据：

**示例**：
```
## 文档驱动工作流效率提升
- Token 使用：减少 60%（通过文件共享而非 context 传递）
- 并行能力：支持同时 3+ 功能规划
- 可回溯性：100%（所有决策都有文档记录）

数据来源：实际使用反馈
```

#### 5. 反模式与警告（Anti-patterns）

记录"什么不该做"（代码里看不出"没做的事"）：

**示例**：
```
## ⚠️ 避免的错误
- ❌ 不要在 context 中传递长文档（使用文件共享）
- ❌ 不要在归档前删除关键决策信息（先上收到架构文档）
- ❌ 不要修改 docs/archive/ 中的文档（归档后不可变）
```

#### 6. 演化历史（Evolution）

记录关键的设计演化：

**示例**：
```
## 工作流设计演化
- v1.0: Agent 直接交互 → 发现 context 浪费严重
- v2.0: 文档驱动工作流 → Token 使用减少 60%
- v2.1: 添加头脑风暴和委托提问 → 需求对齐更准确
```

### 禁止的内容

#### ❌ 不要重复代码

**错误示例**：
> GetCacheKey 方法接受 source, target, text 参数，返回缓存键。

**正确做法**：
如果只是描述代码逻辑，不要写文档。只记录"为什么这样设计"。

#### ❌ 不要模糊描述

错误：系统支持多种缓存策略
正确：系统当前只支持 SQLite 缓存（v2.0），未来可能支持 Redis（🕒 待评估）

## 1. 目录角色与边界

### 1.1 `docs/`

- 存放整个系统和各子系统的**高层架构文档**与当前行为说明。
- 特点：
  - 内容必须始终与当前代码实现保持一致；
  - 面向"现在应如何工作"的问题，而不是历史版本；
  - 适合作为修改代码前的首选阅读入口。

### 1.2 `docs/current/`

- 存放正在执行或尚未完全落地的**详细设计、迁移方案和实施计划**。
- 适用场景：
  - 某个子系统正在重构或迁移，需要一份较长的设计说明；
  - 有多阶段实施计划，需要记录阶段目标、迁移路径和潜在风险；
  - 正在迭代的方案，尚未稳定为"当前权威行为"。
- 要求：
  - 文档应标明"目标状态"和"与现状的差异"；
  - 当设计全部落地并稳定后，应将结论上收合并到 `docs/` 下的架构文档中，并视情况将原文档归档到 `docs/archive/`。

### 1.3 `docs/archive/`

- 存放**历史文档**，包括：
  - 旧版架构设计稿；
  - 已完成的迁移/实施计划；
  - 被新架构取代的方案；
  - 不再代表当前行为、仅用于回顾与考古的资料。
- 要求：
  - 不应继续在归档文档上做"当前行为"的修改；
  - 如需更新现行设计，应在 `docs/` 或 `docs/current/` 中新增/修改对应文档，而不是修改 archive 内容。

## 2. 归档命名规则

归档文档统一按照以下规则组织：

- **功能规划目录（整目录归档）**：`docs/archive/<YYYY-MM-DD>/<feature_name>/`
  - 将 `docs/current/{feature_name}/` 整目录移入
  - 示例：`docs/archive/2026-02-10/oauth2-login/`
- **独立文档（单文件归档）**：`docs/archive/<YYYY-MM-DD>/<BaseName>.history.md`
  - `.history.md` 后缀标识为归档历史文件
  - 示例：`docs/archive/2026-02-10/project-restructure-design.history.md`
- 约束：
  - `<YYYY-MM-DD>` 为归档日期，用于区分不同批次；
  - 同一归档日期目录下不应出现同名文件；
  - 如需多次归档，可在不同日期目录中创建新的归档文件。

## 3. 归档前的 AI 职责（详细流程）

当 AI 需要将某个文档从"当前/设计中"状态迁移到 `docs/archive/` 时，应遵循以下步骤：

1. **确认归档理由**
   - 判断该文档是否已完成历史使命，例如：
     - 相关设计已完全落地，并在 `docs/` 中有了更权威的总结；
     - 该方案已被新的架构取代，不再代表当前实现；
     - 仅保留以供回顾，不再作为日常开发的依据。

2. **上收仍然有效的结论**
   - 阅读将要归档的文档，提取仍然对当前实现有指导意义的结论或约束：
     - 与现行行为完全一致的部分，应合并到对应的文档（如 `README.md`、`docs/workflow.md`、`docs/platform-comparison.md` 等）；
     - 对现行行为仍有直接影响的设计原则，应在相关文档中以更精炼的方式表达；
   - 避免出现"关键信息只在 archive 里存在"的情况。

3. **更新相关文档**
   - 在合适的文档中：
     - 补充或更新对应章节，确保其完整反映当前状态；
     - 如有必要，可以增加"演化历史"小节，简要说明设计演进，但不需要搬运全部历史细节。

4. **在待归档文档顶部添加状态说明块**
   - 在原文顶部增加一个简短的"状态说明"区块，包含：
     - 文档已完成/被取代；
     - 当前权威文档所在位置（例如：`README.md`、`docs/workflow.md`）；
     - 此文档仅作为历史参考，不再代表当前状态。

5. **移动文档到 `docs/archive/` 并按规则命名**
   - 按照第 2 节的命名规范，将文档移动到对应日期目录下。
   - 如当日已存在同名文件，应确认是否确实需要再保留一份，避免重复。

6. **更新其他文档中的链接与引用**
   - 搜索项目中对该文档的引用：
     - 将"当前状态"相关的链接更新为指向主文档（如 `README.md`、`docs/workflow.md`）；
     - 只有在描述历史背景或设计演进时，才保留指向 archive 文档的链接；
   - 确保任何"使用前应阅读"的提示，都指向非 archive 的文档。

## 4. 链接与引用的推荐约定

- **当前状态 / 使用说明**：
  - 链接目标应为主文档，例如 `README.md`、`docs/workflow.md`、`docs/platform-comparison.md`。
- **进行中规划 / 功能设计**：
  - 链接目标应为 `docs/current/{feature_name}/` 下的文档。
- **历史背景 / 演化过程**：
  - 可以在主文档中加入"演化历史"小节，并在其中引用 `docs/archive/` 下的文档。

## 5. AI 操作提示

- 在对文档体系做任何"结构性调整"（新增/归档/大规模重写）前：
  - 应先阅读本规范和相关文档；
  - 在回复中向用户说明预期影响范围，并征求确认。
- 当用户要求"精简文档"或"归档旧文档"时：
  - 优先保证主文档（`README.md`、`docs/workflow.md` 等）的完整性和权威性；
  - 仅在确认不再需要作为"当前参考"时，才将文档移动到 `docs/archive/`。
- 在生成或修改文档时：
  - 保持文档语言为中文；
  - 对代码片段中的注释使用英文；
  - 避免在多个文档中重复维护完全相同的长段说明，优先通过链接复用内容。
- 在归档功能规划文档时：
  - 先将实施后的关键决策上收到相关文档（如 `README.md` 的架构说明）；
  - 再将完整的规划过程（research、clarifications（含决策摘要）、hlplan（如有）、lwplan）归档到 `docs/archive/<YYYY-MM-DD>/<feature_name>/`。
